# Translations and Language Packs

Status: **provisional**. No translation or language-pack functionality is
implemented yet. This document records the direction agreed for the suite, the
parts that remain open, and the validation requirements that apply when the
feature is implemented. It applies to the Hub, the three editors, and to
strings owned by shared libraries.

A placeholder directory (currently `languages/`, with its own README) exists in
the repository root. Its final name and layout are provisional; no code
references it yet.

## Goal

Deliver corrected and updated translations without requiring a full
application release, while keeping the applications fully usable offline and
keeping most work local. Fixing a wording mistake should not wait for the next
build, installer, signing, and notarization cycle; publishing a compiled
translation should be enough for installed applications to pick it up.

## Motivation

- Translations are content: they change more often than code, and reviewing a
  wording fix is far cheaper than producing a release.
- The project is currently maintained by a single developer, whose release
  overhead (three platforms, installers, signing) dominates the cost of a
  translation fix.
- As an open-source project, merged translation contributions should reach
  users quickly instead of being held for the next application release.

## Translation Workflow (provisional)

- User-facing strings are written with Qt's `tr()` mechanism using stable,
  class-based contexts.
- `.ts` files are the source of truth for translations and are committed to
  the repository.
- `.qm` files are build artifacts: generated by Qt 6's translation tooling
  (`lupdate`/`lrelease`, or Qt 6's CMake translation functions) and not
  committed to the main branch.
- Each application embeds its compiled `.qm` files as resources. Bundled
  translations are canonical: they ship with every build and remain the final
  fallback in every scenario.
- The first version follows the system locale. An in-app language override and
  switching without restart are not part of the first version.

## Language-Pack Delivery (provisional)

### Channel

The project's own GitHub repository is the distribution channel; no separate
online service is introduced. Candidate mechanisms:

- fetching a raw file from a dedicated branch (for example `language-packs`);
- fetching a file attached to a GitHub Release.

The repository is public; no authentication is required for either mechanism,
and HTTPS is mandatory. The request sends no user or project data. The client
uses Qt's existing network stack, which is already a project dependency (the
updater), so no new third-party dependency is introduced.

### Manifest

A small JSON manifest lists the available packs. It mirrors the conventions
already established by the update catalog in
[`WINDOWS_UPDATES.md`](WINDOWS_UPDATES.md) (`schema_version`, `size_bytes`,
`sha256`):

```json
{
  "schema_version": 1,
  "packs": [
    {
      "application": "hub",
      "locale": "pt_BR",
      "pack_version": 1,
      "asset": "hub_pt_BR.qm",
      "size_bytes": 123456,
      "sha256": "<64 lowercase hexadecimal characters>"
    }
  ]
}
```

### Client Behavior

- The check runs asynchronously after startup (or on demand) and never blocks
  startup or the user interface.
- Downloads go to a temporary file. A pack is accepted only after its byte
  count and SHA-256 match the manifest and its schema version is supported.
- Installation is atomic: verify first, then replace. The previous pack remains
  until the new one is verified; a failed or interrupted download leaves the
  current state untouched.
- A pack that is stale relative to the application must degrade gracefully:
  strings that no longer match a context are treated as untranslated and fall
  back to the bundled translation or the source text. Qt resolves strings per
  context, so stale packs degrade to untranslated text, never to broken
  behavior.
- The bundled translations always remain the final fallback, and the
  application must remain fully functional offline.

### Loader Precedence

At startup, each application resolves translations in this order:

1. the per-user language-pack directory (downloaded packs);
2. the bundled `.qm` resources.

This contract is what the editors must implement regardless of who performs
downloads. The Hub is the natural owner of downloading and installing packs,
since it already owns per-app updates and shared per-user storage.

## Trust Model (provisional; signing still open)

Phase 1 — repository as trust root:

- HTTPS plus the manifest's size and hash values protect against download
  corruption and incomplete files.
- They do not protect against a tampered source: whoever can change the branch
  or the release can change the manifest and the packs consistently. Such a
  change would reach every installed application without a release build.
- This risk is accepted provisionally while the project is early-stage, and its
  impact is bounded: Qt treats packs as data, so the practical effect is
  limited to displayed text.
- Rejection rules (schema version, size, hash, format) apply before any pack
  reaches the loader.

Phase 2 — verification by signature:

- Packs or the manifest are signed, and the application verifies them against a
  public key embedded at build time, with the private key kept offline.
- This is the target endgame. Open questions: when signing becomes mandatory
  (proposed: before the language-pack channel serves a wider audience) and key
  custody by a single maintainer.
- The suite should keep a single trust model: language packs should follow the
  same trust and verification approach as the Hub updater rather than creating
  a second, weaker channel.

## Open Questions

- Final directory name and layout (`languages/`, `translations/`, or `i18n/`).
- Delivery mechanism: dedicated branch versus release assets.
- Pack granularity: per-application packs, a shared pack for library strings,
  or both.
- Whether the editors self-check for packs when the Hub is never opened.
- In-app language override behavior.
- Translator attribution, licensing, and provenance policy for contributions.

## Validation Requirements (when implemented)

Automated coverage, per [`REGRESSION_POLICY.md`](REGRESSION_POLICY.md), at the
pack boundary:

- manifest parsing: malformed JSON, unsupported schema version, missing or
  invalid hashes and sizes, unsafe asset names;
- verification: corrupted, incomplete, or mismatched-hash packs are rejected;
- atomic installation: an interrupted replacement leaves the previous pack
  usable;
- loader precedence: a valid external pack overrides the bundled one; a
  rejected pack falls back to the bundled one.

Manual checks:

- offline: the application starts and uses bundled translations; the check
  fails quietly and is logged;
- end to end: publish a changed pack and verify that an installed application
  picks it up without a new application build;
- rollback: keep the last known good pack when a downloaded pack is later
  found invalid.

Failures (network, verification, installation) are logged with diagnostic
context and without credentials, following section 8 of `AGENTS.md`. A failed
background translation check is not a user error and must not surface as one.

## Alternatives Considered

- **Bundle translations only in releases.** Simplest, and it remains the
  baseline delivery. Rejected as the only path because every wording fix would
  wait for a full release cycle.
- **A dedicated translation service or CDN.** Rejected for now: additional
  maintenance, a second online dependency, and no benefit at the current
  scale.
- **Downloading packs without integrity data.** Rejected: silent corruption
  risk and no version gate.

## Sequencing

1. Current: placeholder directory and this design document.
2. Bundled translations: `.ts` sources, generated `.qm`, loader precedence, no
   network code.
3. Language-pack channel: manifest in the repository and Hub-managed download
   and installation.
4. Signature verification before the channel serves a wider audience.
