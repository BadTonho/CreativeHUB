# Video Editor audit — 2026-10-12

## Outcome and scope

The audit reproduced **10 functional defects: nine high-priority findings
(P1) and one medium-priority finding (P2)**. The most consequential defects
affect recovery durability, audio integrity, and preview/export consistency.
The existing automated suite passed the selected gate but does not cover the
failing scenarios described below. The initial audit did not implement fixes
or establish release acceptance. Subsequent corrections are tracked below;
the evidence in the findings records the original failing behavior.

| Finding | Correction status | Regression evidence |
| --- | --- | --- |
| F01 | Corrected | `creative-suite-main-editor-autosave`: newer corrupt main, missing main, valid newer main, identical documents, and diagnostics. |
| F02 | Corrected | MainWindow recovery durability: retention across session destruction/failed save, successful Save/Save As cleanup, and explicit Discard. |
| F03 | Corrected | Audio playback tests: complete identical PCM across block limits, mono/stereo resampling, final drain, buffered cancellation, and reset. |
| F04 | Corrected | WAV/AAC PCM comparisons after forward/backward seeks, codec priming, rational resampling, and continuous reads. |
| F05 | Corrected | Render export: shared/isolated precedence, missing-output fallback, offline originals, Fusion inputs, and real masked PNG producer publication. |
| F06 | Corrected | Render export: Motion publication, clip-local time, rate conversion, retained original trimmed audio, missing publication, and offline original with audio disabled. |
| F07 | Corrected | Motion split/trim offsets, history, v25 round-trip/v24 migration, Preview/Fusion/export continuity, and Hub relocation coverage. |
| F08–F10 | Open | Original reproductions below. |

The source review used revision `9a4896b` on `main` with an initially clean
working tree. It covered project persistence and validation, autosave and
recovery, media import and decoding, Timeline editing and history, playback
and audio mixing, Fusion evaluation, export and the render queue, linked
Image Editor/Motion Studio assets, error logging, and the relevant architecture
and regression documents. Shared media/rendering boundaries were included
where they serve the Video Editor.

Validation ran on the local Windows machine with MSVC 19.44, Qt 6.7.2,
FFmpeg libraries including libavcodec 61.19.101, and the available NVIDIA
hardware. Dates in this report use America/Sao_Paulo; some logs contain
2026-10-13 UTC timestamps from the same local evening.

P1 means a defect that can lose recoverable work, corrupt media timing/content,
or produce materially incorrect output in an implemented workflow. P2 means
a narrower failure that blocks an otherwise valid operation. No P0 finding
was established in this audit. Priorities describe repair urgency, not the
acceptance status of an entire application or platform.

## Confirmed findings

| --- | --- | --- | --- |

### F01 — Corrupt main project hides valid recovery snapshots

**Location:** [autosave_manager.cpp](../../apps/video-editor/src/project/autosave_manager.cpp),
`recoverableSnapshotsForProject`, lines 272–299, especially 276–291.

**Reproduction:** save a valid project, write a different valid autosave, then
overwrite the main project with invalid content after that snapshot. The probe
set the snapshot modification time ten seconds earlier to make the ordering
deterministic. Result: `recovery_valid=1 offered_for_corrupt_main=0`.

**Cause and impact:** filtering discards snapshots older than the main file
even when loading that main file failed. The damaged write is therefore
treated as a newer usable save. A missing main file also returns an empty
recovery list when its modification time cannot be obtained; that related
case was identified in source, not separately exercised by the probe.
The valid snapshots remain on disk and can be listed through the Settings
snapshot view; this defect excludes them from automatic recovery discovery.

**Coverage gap:** the existing
[autosave manager test](../../apps/video-editor/tests/project/autosave_manager_test.cpp)
sets every snapshot timestamp two seconds after the main project before
testing corruption (lines 73–98). It misses the normal older-snapshot case.

**Repair and regression:** apply freshness/equality filtering only against
a readable, valid main project. Preserve valid recovery candidates when the
main file is corrupt or unavailable. Test older snapshots followed by a corrupt
write, a deleted main file, identical valid documents, and normal newer saves.

### F02 — Recovery cleanup removes the last durable recovered copy

**Location:** [main_window_project.cpp](../../apps/video-editor/src/main_window/main_window_project.cpp),
`restoreAutosaveSnapshot`, lines 310–342, and the File Open recovery callback
around line 655. The startup unsaved-project recovery callback in
[main_window.cpp](../../apps/video-editor/src/main_window/main_window.cpp)
around line 271 has the same cleanup pattern.

**Reproduction:** save a project with Timeline zoom 1, autosave zoom 2, restore
the snapshot, wait for asynchronous loading, and inspect memory, disk, and
the recovery directory before saving. Autosave was disabled in this isolated
test to expose the interval without a replacement snapshot.

```text
restore_accepted=1 restore_finished=1 dirty=1
in_memory_zoom=2 on_disk_zoom=1 remaining_snapshots=0
```

**Cause and impact:** successful loading triggers removal of the recovery set,
although the recovered document is still dirty and exists only in memory.
A process termination before Save or a subsequent autosave loses the recovered
changes. This finding concerns successful restoration, not an intentional
user decision to discard changes.

**Repair and regression:** retain a valid recovered copy until a successful
durable save or verified replacement recovery write. Test restore followed by
termination without saving, then recovery in a second session; also test failed
saves, saved/unsaved projects, and explicit discard behavior. The ordinary
MainWindow integration test disables autosave, so its passing result does not
establish recovery durability.

### F03 — Audio block limits discard decoded samples

**Location:** [audio_playback.cpp](../../apps/video-editor/src/media/audio_playback.cpp),
`decode_samples`, lines 415–463, especially 459–463. The normal worker requests
4096 samples in [playback_worker.cpp](../../apps/video-editor/src/playback/playback_worker.cpp)
around line 1866.

**Reproduction:** decode the same one-second mono 48 kHz WAV sequentially with
different block limits: 8192 returns 48,000 samples; 512 returns only 6,144.
A one-second 48 kHz FLAC encoded with 8192-sample frames returns 48,000 with
limit 16,384 but only 24,576 with the normal 4096 limit.

**Cause and impact:** the whole codec frame is converted, then the returned
vector is truncated to `maximum_samples`. Excess PCM is not retained for the
next call. The decoder advances past that input while its logical sample
index advances only by the truncated result. This loses content and compresses
the apparent audio duration, affecting playback and export consumers.

The probe also observed 47,983 output samples when resampling a one-second
44.1 kHz FLAC to 48 kHz, consistent with a separate end-of-stream resampler
drain gap. That small tail discrepancy is recorded here rather than counted
as an additional finding.

**Repair and regression:** retain unreturned PCM, maintain correct sample
indices, and drain the resampler at EOF. Assert identical full decoded PCM and
sample counts across several block sizes, including codec frames larger than
the limit, mono/stereo, resampling, and short final blocks. Positive sample
counts and eventual EOF alone are insufficient checks.

### F04 — Audio seeking does not align PCM with its reported position

**Location:** [audio_playback.cpp](../../apps/video-editor/src/media/audio_playback.cpp),
`seek_to_sample_index` around line 353 and chunk indexing/trimming around
432–455. The timestamp-to-sample helper around line 91 is unused.

**Reproduction:** sequentially decode a synthetic AAC chirp as the reference,
seek a new session to sample 12,345, and compare the next 512 samples with the
same slice of the sequential decode. The returned index is 12,345, but the
mean absolute difference is **9,121.1 PCM units**.

**Cause and impact:** backward codec seeking can land before the requested
sample. The code immediately sets its current sample index to the requested
value and labels decoded PCM with that value instead of deriving its real
position from the decoded timestamp. The preroll trimming condition therefore
cannot remove the actual earlier content. Merely asserting the returned index
would pass while the sound is wrong. Export also seeks audio sessions by block
in [offline_export_renderer.cpp](../../apps/video-editor/src/rendering/offline_export_renderer.cpp)
around line 711.

**Repair and regression:** derive actual decoded positions from timestamps
with a defined stream-start and resampler-delay policy, discard real preroll,
and compare PCM against sequential decoding after non-packet-aligned seeks.
Cover AAC and other compressed audio, nonzero stream starts, trim boundaries,
repeated seeks, and preview/export synchronization.

### F05 — Shared Image Editor publication is absent from export

**Location:** [offline_export_renderer.cpp](../../apps/video-editor/src/rendering/offline_export_renderer.cpp),
`clipPath`, lines 142–151, and clip preparation around line 560.

**Reproduction:** create a red original image and a green published image,
attach an Image Editor link to the project's Media Pool entry, and export a
Timeline clip using that entry without a per-clip variant. The center pixel of
the exported frame is `(253, 0, 0)` rather than green.

**Cause and impact:** export resolves a per-clip `image_editor_variant`, then
falls back to `clip.source_path`; it never resolves the shared
`ProjectMedia::image_editor_link`. The original identity intentionally stays
stable, while the preview's refreshed media can represent the publication.
The resulting export silently omits the shared image edit. Existing export
coverage for isolated clip variants does not cover this Media Pool path.

**Repair and regression:** define consistent effective-source resolution for
clip variants, shared publications, and original-source fallback. Compare
preview/export for shared and isolated links, republishing, offline/invalid
publications, and Fusion Media Pool inputs. Any correction must validate the
affected Image Editor producer and Video Editor consumer boundary.

### F06 — Motion Studio publication is absent from Timeline export

**Location:** the same export `clipPath` and preparation code as F05.
For comparison, [playback_controller.cpp](../../apps/video-editor/src/playback/playback_controller.cpp)
around lines 287–289 forwards `linked_render_path`, and
[playback_worker.cpp](../../apps/video-editor/src/playback/playback_worker.cpp)
around lines 794–816 opens the published render with an original-source fallback.

**Reproduction:** use a red original video and a green published video with a
Timeline `motion_link`. Export returns `(252, 0, 0)`, the original red frame,
instead of the publication.

**Cause and impact:** export ignores `clip.motion_link`. A working linked
preview does not imply that the final render contains the composition.

**Repair and regression:** share a documented effective-render contract across
preview/export, including publication fallback and the published clip's time
origin. Preserve the intended original-audio behavior when switching visual
sources. Test producer/consumer publication, trimmed clips, mixed frame rates,
republishing, missing publications, and final exported frames/audio.

### F07 — Splitting a linked clip restarts its published animation

**Location:** [timeline_model.cpp](../../apps/video-editor/src/timeline/timeline_model.cpp),
`splitClip` around lines 1743–1751, and
[playback_worker.cpp](../../apps/video-editor/src/playback/playback_worker.cpp),
linked source-frame selection around lines 2788–2790.

**Reproduction:** link a one-second 30 fps clip to a published render that is
red for the first half and green for the second half. Inspect Timeline frame
15, split at frame 15, and inspect that same frame in the right clip. Before
the split the pixel is `(0, 254, 0)`; afterward it is `(253, 0, 0)`.

**Cause and impact:** split copies the Motion link and advances the original
source offset, but the worker selects linked frames using the new clip-local
frame, which starts at zero. A structural edit changes visible content at an
unchanged Timeline position. Similar trim/rate-change interactions require
additional coverage; they were not separately reproduced here.

**Repair and regression:** preserve the linked render's origin/range across
editing, or explicitly regenerate a compatible publication. Verify continuity
before/after split and trim, undo/redo, Save/reopen, mixed rates, and transitions.
If a new persisted offset is required, cover older supported project formats.

### F08 — CPU conversion uses the wrong matrix for tagged BT.709 video

**Location:** [video_playback.cpp](../../libs/media/src/video_playback.cpp),
RGBA conversion around lines 197–216.

**Reproduction:** decode a synthetic red FFV1 frame explicitly tagged BT.709
and compare it with FFmpeg's metadata-aware conversion of the same file. The
application returns `(230, 0, 0)`; the reference returns `(251, 0, 0)`. This is
an ordinary SDR matrix discrepancy, not an HDR acceptance request.

**Cause and impact:** `sws_getCachedContext` is used without configuring
`sws_setColorspaceDetails` from the frame/stream matrix and range. The converted
RGBA loses the information needed to correct this later. Common source colors
can therefore differ materially from their intended values. CPU/GPU parity
against a shared wrong reference does not establish color correctness; native
GPU color correctness for this fixture was not separately tested.

**Repair and regression:** honor matrix/range metadata with a documented
fallback, and reconfigure a cached converter when those properties change.
Use independent expected values for BT.601/BT.709, full/limited range, and
source switches. Validate every affected preview/export backend.

### F09 — Video display rotation is ignored

**Location:** [video_playback.cpp](../../libs/media/src/video_playback.cpp),
output geometry around lines 189–190 and conversion around 197–216;
[video_metadata.h](../../libs/media/include/creative_suite/media/video_metadata.h)
does not expose a video display-transform contract.

**Reproduction:** remux a 32×16 MP4 with a 90-degree display rotation matrix.
Application decoding returns unrotated 32×16 geometry rather than the expected
16×32 displayed frame.

**Cause and impact:** the media pipeline uses coded frame dimensions and
pixels without applying the container's display transform. Phone/camera videos
that use this metadata can appear sideways and export incorrectly. The still
image reader already uses automatic orientation; that does not cover videos.

**Repair and regression:** define how orientation maps to displayed geometry,
preview, export, transforms, and selection/hit testing. Cover 90/180/270-degree
rotations and mirrored display matrices. Pixel aspect ratio is a related
metadata concern that needs its own fixture; it was not proven by this test.

### F10 — Disabled audio export still rejects an offline audio-only source

**Location:** [offline_export_renderer.cpp](../../apps/video-editor/src/rendering/offline_export_renderer.cpp),
clip preparation around lines 560–574.

**Reproduction:** add a missing audio-only WAV clip to a valid image project
and export with `export_audio=false`. Export fails with
`Media is offline or unreadable: ...missing-audio.wav`.

**Cause and impact:** file existence is checked for every non-text clip before
the audio-enabled condition. A source that contributes no output still blocks
the entire video-only render.

**Repair and regression:** avoid preparing unneeded audio-only sources while
preserving the specified Timeline duration and any expected visual tail.
Test video-only export with missing audio, normal audio-enabled failure,
audio-only tails, and cancellation/destination preservation.

## Performance and robustness risks requiring measurement

These are source-based risks or incomplete acceptance, not additional
reproduced functional defects.

- **Media Pool memory:** each
  [MediaItem](../../libs/media/include/creative_suite/media/media_library.h)
  owns a `VideoFrame first_frame` (line 19),
  [media_importer.cpp](../../libs/media/src/media_importer.cpp) decodes a full
  first frame (lines 38–56), and
  [media_library.cpp](../../libs/media/src/media_library.cpp) retains it
  (around line 100). One 3840×2160 RGBA frame occupies about 31.64 MiB;
  100 such retained frames alone occupy about 3.09 GiB, excluding other
  caches and application state. Measure actual imports and resident memory
  before choosing thumbnails, bounded full-frame caches, or lazy decoding.
- **Large project opening:**
  [project_file_reader.cpp](../../apps/video-editor/src/project/project_file_reader.cpp)
  reads the whole JSON file before parsing (line 567). The overlap check in
  [project_document_validator.cpp](../../apps/video-editor/src/project/project_document_validator.cpp)
  compares every pair of clips per track (lines 386–389), with further
  transition scans. Large or hostile documents need memory/time budgets,
  cancellation measurements, and malformed-input tests. No OOM or hang from
  this path was reproduced during the audit.
- **Physical smoothness and workload scaling:** existing documented offscreen
  GPU measurements do not establish native display/audio acceptance. Repeat
  representative small, medium, and heavy projects on the physical UI with
  latency, dropped frames, memory, startup, seek, and export measurements.
- **Portability:** this local run covers Windows only. Preserve the CI matrix
  and separately record native macOS/Linux devices, codecs, graphics drivers,
  packaged runtime, and update/recovery acceptance.

The inspected error paths and existing logging tests provide useful baseline
coverage, but passing synthetic tests does not validate every corrupted-media,
resource-shortage, or device-loss scenario. Extend fault injection alongside
repairs rather than treating the current pass count as a complete safety proof.

## Documentation inconsistencies

The implementation's project schema is **24**
([project_document.h](../../apps/video-editor/src/project/project_document.h),
line 16). The following older statements should be reconciled in subsequent
implementation/documentation work:

- [architecture/SCOPE.md](architecture/SCOPE.md), line 22, still describes
  persistence through version 23; its deferred list includes GPU
  effects/decoding/encoding, animated node parameters, and linked Motion Studio
  handoff despite implemented paths documented elsewhere. Its proposed OS
  file-drop work also overlaps already implemented regression coverage.
- [architecture/PROJECT.md](architecture/PROJECT.md), line 108, says the next
  save produces a normalized version 23 document, while the same document's
  current-format section correctly describes ordinary saves as version 24.

Implemented behavior, passing tests, and release acceptance should remain
separate statuses. The contradictions above can otherwise obscure whether a
workflow is missing, experimental, or implemented with an open defect.

## Recommended repair order

1. Protect recovery durability and candidate discovery (F01–F02).
2. Preserve all decoded audio and correct seek alignment (F03–F04).
3. Align effective sources and linked time origins across editing,
   preview, and export (F05–F07), with producer/consumer regression coverage.
4. Correct color/orientation metadata handling (F08–F09).
5. Remove the unnecessary offline-audio dependency (F10), resolve the local
   deployment blocker, and reconcile the stale documentation.

Each repair needs observable regression coverage in the same change and the
affected feature-to-verification entries updated under
[the repository regression policy](../REGRESSION_POLICY.md). Then rerun a
fresh scoped build, the affected automated gates, and the remaining manual
acceptance checks before preparing a release.
